# Spec: Wholesome Animal Video Feed (working title)

A tiny, self-maintaining web tool that plays a short, curated feed of animal
videos from YouTube — a deliberate, joyful alternative to doom-scrolling. The
user picks how long they want to watch up front; the tool honors that and ends
gently.

This document is a build spec for Claude Code. Build it in a fresh GitHub
repository from the first commit — the scheduled content refresh depends on
GitHub Actions, so the repo is part of the architecture, not an afterthought.

---

## Goals & non-goals

**Goals**
- Play a short session of wholesome animal videos, no news / politics / influencers.
- **Zero ongoing content curation.** New videos appear automatically as the
  curated channels post them. The only thing the maintainer edits by hand is a
  short list of channel IDs (rarely) and a small blocklist (when something slips
  through).
- Let the viewer set an *intention* up front ("Got 2 minutes? 5? 10?") that
  drives session length and video selection.
- End the session warmly, never with guilt. This is a wholesome alternative, not
  a scold.
- Stay free: no runtime API calls from the browser, no exposed API key, well
  within YouTube's free daily quota.

**Non-goals (v1)**
- No user accounts, no social features, no uploads, no comments.
- No true content *understanding*. Guardrails are metadata pattern-matching, not
  a vision/LLM pass. (See "Guardrails" — this is a deliberate, stated limitation.)
- No native mobile app. Responsive web only.
- No Instagram. (Deprecated oEmbed, review-gated tokens, platform terms hostile
  to a competing consumption surface, fragile embeds. Explicitly out of scope.)

## Architecture overview

Two clean halves with a static JSON file as the seam between them:

```
  channels.json  ──►  build script (Node, scheduled) ──►  videos.json  ──►  static front-end
  blocklist.json ──►        (calls YouTube API)                              (no API calls)
```

1. **Build step** runs on a schedule via GitHub Actions. It reads the config,
   calls the YouTube Data API, filters for drift, buckets videos by duration,
   and writes a static `videos.json`.
2. **Front-end** is fully static (single page, no framework required). It fetches
   `videos.json`, shows the duration picker, and plays videos via the YouTube
   IFrame Player API. **It never touches the YouTube Data API**, so it exposes no
   key and consumes no quota no matter how many people use it.

This separation is the whole trick: all secrets, all API cost, and all filtering
logic live in the scheduled build; the deployed site is dumb, static, and safe.

### Why this keeps us in the free tier
- YouTube Data API v3 gives 10,000 quota units/day free, no credit card.
- `playlistItems.list` and `videos.list` cost **1 unit** per call; `search.list`
  costs **100**. **Never call `search.list`.** Discovery is by channel, not search.
- Every channel has an "uploads" playlist whose ID is the channel ID with the
  `UC` prefix swapped for `UU`. Paging that playlist is how we get a channel's
  recent uploads at 1 unit per 50 videos.
- Tracking dozens of channels daily costs a few dozen units — a rounding error
  against 10,000.

```
/
├── config/
│   ├── channels.json        # curated channel IDs (the main maintenance surface)
│   ├── blocklist.json        # video IDs to never show (reactive, rare)
│   └── denylist.json         # title/description keyword filters for drift
├── scripts/
│   └── build-feed.mjs        # the scheduled build script (Node, ESM)
├── public/                   # the deployed static site
│   ├── index.html
│   ├── app.js
│   ├── style.css
│   └── videos.json           # GENERATED by build-feed.mjs; committed by the Action
├── .github/workflows/
│   └── refresh-feed.yml       # scheduled build + commit
├── package.json
├── README.md
└── SPEC.md                    # this file
```

Keep `videos.json` in `public/` and let the Action commit it, so the site can be
served by any static host (GitHub Pages, Netlify, Cloudflare Pages) with no build
step of its own.

## Config files (the agent- and human-editable surface)

Design these so a human *or* an agent (Claude Code, a future script) can safely
read and edit them without touching code. Plain JSON, one concern per file,
documented inline via a sibling `.md` or header comment where the format allows.

### `config/channels.json`
The primary maintenance surface. A list of channels to pull uploads from.

```json
{
  "channels": [
    { "id": "UCxxxxxxxxxxxxxxxxxxxxxx", "label": "Monterey Bay Aquarium", "trust": "high" },
    { "id": "UCyyyyyyyyyyyyyyyyyyyyyy", "label": "Some Pet Creator", "trust": "medium" }
  ],
  "maxVideosPerChannel": 20,
  "maxAgeMonths": 12
}
```
- `trust` is advisory metadata for future tuning (e.g. apply stricter filters to
  `medium`); v1 may treat all channels equally but must preserve the field.
- `maxAgeMonths` limits how far back we vouch for a channel's back-catalog and
  keeps the feed fresh.

### `config/denylist.json`
Case-insensitive substring/keyword matches against title + description. Drop any
video that matches. Seed it with obvious drift categories; keep it editable.

```json
{
  "keywords": [
    "urgent", "please help", "gofundme", "donate now",
    "rainbow bridge", "passed away", "in memory of", "rip ",
    "breaking", "politics", "election"
  ],
  "notes": "Substring match, case-insensitive, on title+description. Tune freely."
}
```
Keep this list conservative — over-filtering silently shrinks the feed. Log every
drop (see build logging) so tuning is evidence-based.

### `config/blocklist.json`
Reactive, per-video overrides. The only routine hand-maintenance.

```json
{ "videoIds": ["dQw4w9WgXcQ"], "notes": "One line per slip-through. Rare." }
```

## Build script — `scripts/build-feed.mjs`

Runnable locally and in CI. Reads config, produces `public/videos.json`.

**Behavior, as discrete steps (keep them separable — atomic over monolithic):**

1. **Load config.** Read `channels.json`, `denylist.json`, `blocklist.json`.
   Fail loudly with a clear message + nonzero exit if any is malformed.
2. **Resolve uploads playlists.** For each channel, derive the uploads playlist
   ID by replacing the leading `UC` with `UU`. (Optionally verify via
   `channels.list` → `contentDetails.relatedPlaylists.uploads`; not required.)
3. **Fetch recent uploads.** `playlistItems.list` per channel, up to
   `maxVideosPerChannel`. Collect video IDs.
4. **Fetch durations + snippets.** Batch video IDs (up to 50 per call) into
   `videos.list` with `part=contentDetails,snippet` to get ISO-8601 duration,
   title, description, publish date, thumbnails.
5. **Filter (drift guardrails):**
   - Drop IDs present in `blocklist.json`.
   - Drop if title/description matches any `denylist.json` keyword.
   - Drop if `publishedAt` older than `maxAgeMonths`.
   - Drop duration outliers: anything longer than a sane cap (default 20 min —
     likely a livestream replay or vlog, not a clip). Make the cap a constant.
   - Drop non-`public` / unavailable videos if detectable.
6. **Bucket by duration:** parse ISO-8601 to seconds and tag each surviving
   video `short` (< 60s), `medium` (60s–4min), `long` (4–20min). Store the tag.
7. **Write `public/videos.json`** — schema below. Sort or shuffle-at-runtime is
   the front-end's job; the file can be publish-date-desc.
8. **Report:** print a summary to STDOUT (counts in / kept / dropped, dropped-by-
   reason breakdown) so drift tuning is evidence-based.

**Flags (agent-friendly, inspectable):**
- `--dry-run` — do everything except write the file; print what *would* be
  written and the full drop report. Essential for tuning the denylist safely.
- `--verbose` — per-video decisions to STDERR.
- Exit `0` on success, nonzero on config/API failure. Errors to STDERR.

**API key:** read from `process.env.YOUTUBE_API_KEY`. Never hardcode, never
commit. Locally, read from a git-ignored `.env`; in CI, from an Actions secret.

**Quota safety:** log estimated units consumed. Guard against a runaway channel
list. This should be structurally impossible to blow the quota, but log it anyway.

### `videos.json` schema
```json
{
  "generatedAt": "2026-08-18T00:00:00Z",
  "videos": [
    {
      "id": "abc123",
      "title": "Otter eats a clam",
      "channel": "Monterey Bay Aquarium",
      "durationSeconds": 47,
      "bucket": "short",
      "publishedAt": "2026-08-10T12:00:00Z",
      "thumbnail": "https://i.ytimg.com/vi/abc123/hqdefault.jpg"
    }
  ]
}
```
Include a top-level `generatedAt` so the front-end (and a human) can see feed
freshness. Keep the schema flat and obvious.

## GitHub Actions — `.github/workflows/refresh-feed.yml`

- **Trigger:** `schedule` (cron — daily is plenty; weekly is fine too) plus
  `workflow_dispatch` for manual runs.
- **Steps:** checkout → setup Node → `npm ci` → run `node scripts/build-feed.mjs`
  with `YOUTUBE_API_KEY` from `secrets.YOUTUBE_API_KEY` → if `public/videos.json`
  changed, commit and push it back to the repo.
- Use a least-privilege token for the commit-back step; document the required
  repo/workflow permission in the README.
- The commit-back is what makes the static host redeploy automatically.

Document in the README: how to create the Google Cloud project, enable YouTube
Data API v3, generate the key, and store it as the `YOUTUBE_API_KEY` Actions
secret (and a local `.env` for dev).

## Front-end — `public/`

Static, framework-optional (vanilla JS is fine and keeps it dependency-free).
No API calls. Fetches `videos.json`, plays via the YouTube IFrame Player API.

### Flow
1. **Intention picker (opening screen).** Friendly, warm copy. Offer a few
   session lengths, e.g. **2 min · 5 min · 10 min**. The choice sets:
   - **Session budget** (total watch time before the gentle end screen).
   - **Bucket preference:** short session → favor `short`; longer session →
     `medium`/`long` mix. Selection logic should degrade gracefully if a bucket
     is thin (fall back to adjacent buckets rather than showing nothing).
2. **Play.** Shuffle the eligible pool, play sequentially. Use the IFrame API's
   state-change / `onEnded` event to auto-advance. Track cumulative watch time
   (or video count) against the session budget.
3. **Gentle end screen.** When the budget is reached, show something warm —
   e.g. "Hope that brightened your day 🐾" — with a single low-key **"a few
   more?"** affordance. **No guilt, no nagging, no counters shaming the user.**
   Setting the intention up front is the nudge; the ending just honors it.

### UX / tone constraints
- Warm, calm, uncluttered. This is an antidote to the algorithmic feed, so it
  should not *feel* like one — no infinite scroll, no autoplay-forever, no
  "you've watched 47 videos" dark patterns.
- Responsive; works one-handed on a phone.
- Respect reduced-motion preferences.
- Minimal chrome during playback — let the animals be the thing.

### Optional (nice-to-have, not v1-blocking)
- A separate, clearly-labeled **live cams** section (zoo/aquarium livestreams).
  These are persistent live streams, not uploads — hardcode a few embed IDs in a
  small `config/livecams.json`; they don't flow through the uploads-playlist
  pipeline and rarely change.
- A "report this video" affordance (simple mailto or form) so the maintainer
  isn't the only one catching drift; reported IDs get hand-added to
  `blocklist.json`.

## Guardrails: stated limitation

The drift defense is **allowlist (curated channels) + denylist (keyword) +
blocklist (manual) + age/duration bounds.** This is metadata pattern-matching,
not content understanding. A cheerful title on a sad video will get through. That
is an accepted v1 tradeoff: the goal is to make drift *rare and quickly fixable*,
not impossible. True screening (vision/LLM pass on thumbnails/transcripts) is
out of scope for v1 and would carry its own cost and complexity. Note it in the
README so the tradeoff is explicit, not accidental.
